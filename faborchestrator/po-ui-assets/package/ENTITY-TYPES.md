## How to use this

1. **If a sample page shows a code for that same column, use that code.** The table below is a
   default, not a derivation — see the warning immediately after this list.
2. Otherwise find the property on its entity below and emit `"type": { "type": <the code> }`.
3. If the property is **not listed** and no sample shows one, it is UNKNOWN — record it in the gap
   report. Do **not** guess.

### ⚠ The database type does not decide the UI code

The codes here are the framework's `PfT` enum, which controls **how a value is RENDERED**. The
database type controls **how it is STORED**. They usually agree, and they are not the same thing —
so a real page may legitimately render a `Decimal` column without decimals.

Measured across the 66 live base-tenant pages, the mapping is **not one-to-one** for three of the
five scalar types that appear:

| DB scalar type | UI codes actually emitted on real pages |
|---|---|
| `BigInt` | `11` ×9 |
| `DateTime` | `2` ×2 |
| **`Decimal`** | **`5` ×4 · `1` ×1** |
| **`Int`** | **`11` ×4 · `5` ×1** |
| **`NVarChar`** | **`4` ×3 · `11` ×1** |

**The worked example, and it is the one that matters most here.** CMF's own stock page
`Cmf_ProductionOrder_Page_Production_Orders` renders **every** production-order quantity as
**Integer (5)** — `Quantity`, `InProgressQuantity`, `CompletedQuantity`, `DeliveredQuantity` — even
though all four are `Decimal` in the schema. Athena's delivered page types `Quantity` **5** as well.
That is **5 of 5 real artifacts**, so for a production-order quantity the evidenced answer is `5`,
not the `1` this table would give you.

This is the same rule that already governs data paths: **evidence from a real artifact beats a
derivation, and a derivation beats a guess.** When you take a code from a sample rather than from the
table below, say so in the gap report so a human can confirm it.

Types with **no** confirmed UI code — treat a column of these as UNKNOWN: *(none among the properties below)*

**`=11*`** means the database type is `BigInt` and the property is usually a **reference to another
entity**. Emit `type: 11` **plus** `referenceType: 1` **plus** `referenceTypeName: "<Entity>"`, and
use that record's `Id` as the path — see DICTIONARY §1. A `BigInt` that is a plain counter
(e.g. `LastOperationHistorySeq`) is **not** a reference; judge from the name and record the
uncertainty if it is not obvious.

## ⚠ Spec terms that are not schema properties

`TrackInResource` and `TrackInId` are named in the requirement document as Material columns.
**Neither is a property of `Material`.** (`Material` has `TrackInDate`, `TrackInPrimaryQuantity`, `TrackInSecondaryQuantity`, `LastProcessedResource`, `LastProcessStepResource`, `LastSetupResource`, `RequiredResource`.)

**This does not mean emit UNKNOWN.** `DICTIONARY.md` records that Athena's own delivered export
maps them to `LastProcessedResource` and `ModifiedBy` — that is evidence of intent from the people who built the page. Use those
paths, take the type from this file (`LastProcessedResource:BigInt=11*`, `ModifiedBy:VarChar=4`), and **raise the naming mismatch in
the gap report** so Athena can confirm.

Absence from this file only forces `UNKNOWN` when **no** source — dictionary, sample, or schema —
provides a path.
